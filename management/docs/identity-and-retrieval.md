# 身份标识与检索

> **一句话**：知道"视频里这只猫是谁、这个碗是哪个猫的、那个摄像头是不是上次那个"。
>
> 这件事分三层——① 在视频里找到并持续跟踪每只猫（**定位追踪**）② 认出"这就是那只特定的白猫"（**个体身份 / 猫 Re-ID**）③ 认出"这个碗就是这个碗"（**物体实例标识**，参考 RAG 的检索增强思路）。

## §0 一句话概览

| 层 | 解决什么问题 | 路线 | 深入 |
|---|---|---|---|
| ① 定位追踪 | 这只猫在每帧哪、同一只猫在跨帧是否保持同一 id | GroundingDINO 多 prompt 抽样 + 插值 + 运动校正 v5（可选，默认禁用） | 本篇 §1 |
| ② 个体身份 | 这只猫是登记过的哪只猫？还是新面孔？ | **embedding 检索**：登记照 → embedding → 向量库最近邻（模型/向量库待实测） | 本篇 §3 |
| ③ 物体实例 | 这个碗是不是上次那只、摄像头是不是同一个机位 | SAM 分割候选 + embedding 检索（同上，待实测） | 本篇 §4 |

**贯穿三层的统一原理——对比学习（contrastive learning）**：
- 同一只猫在走路/睡觉/跑酷的不同视频帧里，提取的特征要**相似**（positive invariance，正样本对拉近）
- 两只不同猫在同一个沙发上，特征要**区分**（negative discrimination，负样本对推远）
- 同一个物体（碗）放在厨房/客厅/被端着走，特征也要相似
- 这个性质在工程上的实现：**embedding 相似度检索**（登记照→embedding→向量库）
- ⚠️ **模型与向量库未定**：具体用哪个 embedding 模型（DINOv2/DINOv3/CLIP/SuperAnimal/猫专用 Re-ID）与哪个向量库（numpy/FAISS）**在 `registry-retrieval` 实施时实测**；DINOv2+FAISS 仅为默认候选
- 身份-动作 Tokenizer 的身份通道走**参考输入条件化**路线（身份「给定」而非推断，监督由重建承担，详 [8 号](../wiki/identity-tokenizer) §4.6）——两条路线共享的仍是「同猫相似、异猫区分」这一原理

## §1 宠物定位与跟踪

### §1.1 是什么 / 为什么需要

每帧输入是 1280×720 或更高的监控画面，输出是"第 N 帧 (x, y, w, h) 这只猫在画面里 + 它的轨迹 id = T123"。所有下游任务的前提——没有它就没有"以猫为中心"和"行为时间轴"。

### §1.2 算法（用白话讲）

四步流水线：

1. **GroundingDINO 检测**（每 10 帧抽 1 帧）
   - GroundingDINO 是一个**开放词汇检测器**——给它文字提示（"cat"），它就在图里框出可能是猫的区域
   - 文字提示不只"cat"一个，还试"feline"、"tabby cat"、"black cat"等若干种，提高召回
   - **为什么每 10 帧抽 1 帧**而不是逐帧跑：监控视频帧率 30fps，全帧率跑 GroundingDINO 算力浪费巨大；白天场景背景稳定，猫的运动慢，抽样+插值已经足够
2. **插值平滑**（中间 9 帧）
   - 抽到的两帧之间有 9 帧是空的，用数学方法（线性/样条）把猫的位置补上
   - 结构性插值率 ≈ 0.905（即 90% 的"无检测帧"是抽样设计造成，**不是异常**）
3. **运动校正 v5**（可选触发）
   - 猫被柱子/家具遮一下又出来，跟丢再重新框时位置可能跳变；运动校正让位置平滑
   - 参数定稿（2026-09-15 三轮迭代后）：off-alpha 0.6 / off-max-v 5% 帧宽 / 覆盖门槛 0.2
   - 实测：校正触发率 12.0%，偏移 max 108px，锚点帧像素级一致
   - **开关默认禁用**——运动校正治标治本有限，关键帧丢就让它丢，渲染层过滤兜底
4. **家具框 + 空间状态序列**
   - 同时输出碗/水碗/砂盆/门/窗户的框（来自 detection-annotation-taxonomy 8 类体系）
   - "猫在碗附近 / 在砂盆附近"这种空间状态用作抽查报告的辅助字段

### §1.2b 为什么不需要 SORT 系列的跟踪器（白话）

**SORT 家族是什么**：**多目标跟踪（MOT）**——给检测框**贴身份编号、维持轨迹**。

**问题的起点：检测器没有记忆**。检测器只会说"这里有个东西"，不会说"这和上一帧那个是不是同一个"：

```
帧1  检测器输出 2 个框    框A(100,200)   框B(500,300)
帧2  检测器输出 2 个框    框C(110,205)   框D(495,298)
问：C 是刚才的 A 还是 B？
```

没有关联 → 手上只有"每帧一堆框"，**说不出"这只猫向右走了 10 像素"**（没法把两帧的框串起来）。有了关联 → 每条轨迹有 id、跨帧保持 → 这才叫"轨迹"。

**SORT 的核心循环**（所有变体共享）：

```
对每条已有轨迹：
  ① 卡尔曼滤波预测它这一帧该在哪（用过去几帧速度外推）→ 预测框
  ② 预测框 vs 本帧检测框 → 算匹配代价（IoU / 外观 / 运动方向）
  ③ 匈牙利算法求【最优一对一匹配】
  ④ 匹配上     → 检测框接进该轨迹（并用它修正滤波状态）
     没匹配上的轨迹 → 标 lost，连续 N 帧没匹配就删（目标离场）
     没匹配上的检测 → 新建轨迹（新目标出现）
```

**家族差异只在这三个决策点**：

| 变体 | 年份 | 关键差别 |
|---|---|---|
| **SORT**（Simple Online and Realtime Tracking）| 2016 | 卡尔曼 + 纯 IoU 匹配（最简）|
| **DeepSORT** | 2017 | 加**外观 Re-ID 特征** → 遮挡后靠"长相"把 id 接回来 |
| **ByteTrack** | 2022 | **不丢低分检测**：先高分关联，再用低分给丢失的轨迹"续命" |
| **OC-SORT** | 2022 | 加**运动方向一致性**；遮挡结束后用新观测**回填被污染的状态** |
| **BoT-SORT** | 2022 | ByteTrack + **相机运动补偿** + 外观融合（工程完成度最高）|

**为什么我们不用**——**场景是单猫**，每帧基本只有 1 个目标，"哪个框是哪个"**几乎不存在**：

```
只有一只猫：
  帧10   检测到 1 个框 → 当然是猫
  帧11~19 没检测（我们每 10 帧才检一次）
  帧20   检测到 1 个框 → 还是猫
  → 把帧10 与帧20 的框插值连起来就够了           【插值就够】

有两只猫：
  帧10   检测到 2 个框   A  B
  帧20   检测到 2 个框   C  D
  → C 是 A 还是 B？必须靠运动/外观判断
  → 判错 → 猫1 的轨迹里混进猫2 的位置             【这才是 SORT 的活】
  → 而且插值在这里帮不上：插值必须先知道"哪两条框属于同一目标"
```

**两者是上下游、不是替代**：

```
SORT  = 有多个候选人时 → 判断谁是谁（贴 id）      ← 我们跳过（只有一个目标）
插值  = 已确定是同一个目标、中间没框 → 补出来      ← 我们用的
```

**现状**：`petlib/tracking/` 有 5 个空壳适配器（包装 BoxMOT 库），**管线从未 import**；管线的"关联"就是一行 `argmax(置信度)`。多猫能力挂在 `tracker-selection` change 上（⏸️ 延后，触发条件 = **多猫数据出现**）。

### §1.3 关键否决与裁定

- **ByteTrack 全帧率版否决**（D1）：单猫场景下"抽样+插值"已验收，全帧率跟踪是过度工程
- **GatedTracker 否决**（D1b）：门控治标不治本；沙发误检由渲染层过滤兜底
- **关键点降级为辅助信号**（D2）：MC 跟随视角实测关键点 mean_conf 0.367，>0.5 帧仅 0.2%，四肢点 <0.25——置信度太差，关键点整体移出管线（仅历史脚本 `extract_keypoints_from_tracks.py` 留作备查）

### §1.4 代码与产物

- 代码：`scripts/pet_detect_track.py`
- 产物：`results/batch/*/track.json`（轨迹 + 家具框 + 空间状态序列）
- 报告：`results/batch/batch_report.md`（34 段白天视频，三率：检出 0.939 / 插值 0.905 / 校正 0.334）
- 验收（2026-09-15）：34/34 完成，三告警段（event_20260806_100505 等）已结案——为超短片段+低在场率+红外域边缘，**非算法故障**

### §1.5 跟随视角生成（紧接定位）

定位后的轨迹直接喂给 `scripts/make_followcam.py`：

- 输出 512×512 以猫为中心的 H.264 视频
- **follow_adaptive**：根据猫在画面里的位置动态调整裁剪框，过滤掉尺寸离群帧（猫跳起跳落那一瞬不造成整段画面乱抖）
- 沙发漂移问题由渲染层过滤兜底
- 详细参数与代码：`scripts/make_followcam.py`

**为什么主表示载体要选跟随视频**：① 模型不用再学"找猫" ② 分辨率不浪费在背景 ③ 帧间变化幅度集中在猫身上利于动作建模。详见 [6 号《系统架构》§4.2](../wiki/architecture)。

## §3 猫个体识别（猫 Re-ID）

### §3.1 什么时候需要

多机位 / 多时段场景下——家里有两台摄像头分别拍客厅和卧室，猫 A 在客厅被拍到后跑到卧室，**怎么知道卧室里的那只就是客厅里的那只而不是另一只**？这就是 Re-ID 要解决的问题。

### §3.2 原理（用白话讲）

四步：

1. **登记**：给每只猫拍几张"身份照"（正脸、侧脸、特征性花纹）存到登记照库
2. **提特征**：用 **embedding 模型**把每张照片变成一串数字（向量）。⚠️ 具体用哪个模型**待实测**（候选：DINOv2 / DINOv3 / CLIP·SigLIP / SuperAnimal / 猫专用 Re-ID）
3. **建索引**：把所有登记照的向量存进**向量库**。⚠️ **先算规模再选工具**——登记库仅几十个向量，默认 numpy 暴力检索即可（FAISS 是十万级以上的工具）
4. **检索**：新出现一只猫时也提一串向量，去向量库里找最像的前 N 个，相似度（向量余弦距离）超过阈值就算"同一只"

未登记个体标"未知猫 #N"——避免在不知道身份时硬猜。

### §3.3 对比学习视角

Re-ID 本质就是对比学习的**检索实现**：

| 概念 | 工程实现 |
|---|---|
| Positive invariance（同猫跨视角/时间应相似） | 同猫登记照的向量在向量库里聚到一起 |
| Negative discrimination（不同猫应区分） | 不同猫的向量在向量库里分开 |
| 检索 | 向量库的相似度查找 |

同一只猫走路/睡觉/跑酷的三段视频帧 → 提 embedding → 应该聚到一起；
两只不同猫在同一个沙发上 → 特征应该分开。

这种性质的根本保证来自 **embedding 模型自身的训练**（自监督对比学习）；向量库只是把这个性质暴露给应用层做查询。

### §3.4 与 8 号身份-动作 Tokenizer 的区别

| | 猫 Re-ID（本篇 §3） | 身份-动作 Tokenizer（[8 号](../wiki/identity-tokenizer)） |
|---|---|---|
| 目标 | 判"谁是谁" | 解耦"身份与动作"，用于重建/生成 |
| 原理 | embedding 检索（模型待实测）| **参考输入条件化** + 容量闸门 + 重建 |
| 身份从哪来 | 登记照检索得出 | **参考输入直接给定** |
| 身份监督 | 隐式（embedding 模型训练时已有） | 重建承担（无需额外身份损失）|
| 输出 | "未知猫 #N" / 某只已登记猫 | 视频重建 / 可控生成 |
| 状态 | 0/4 待批准实施（`registry-retrieval`） | 0/9 研究型（`identity-action-tokenizer`） |

- 代码：`scripts/register_cats.py`（计划中）
- 索引文件：向量索引位置待定（应在 `data/` 或 pet 远程）；**向量库选型待实测**（见 `registry-retrieval` design D9b）
- 关联字段：spot-check-cli 的"登记身份"列

## §4 RAG 式物体实例标识

### §4.1 为什么叫"RAG 式"

RAG（Retrieval-Augmented Generation）核心是"先检索后生成"——不靠模型凭空生成，而是先用检索器找相关材料。这里借用其思路：**不靠模型直接说"这个碗是 A 碗"**，而是预先把每个物体"登记入库"，新帧去库里检索最像的那个。

### §4.2 物体实例的特殊性

猫 Re-ID 与物体实例识别原理相同（同 embedding 检索 + 对比学习），但物体有几条额外的麻烦：

- **边界模糊**：碗、砂盆、摄像头在画面里有多大算"这个碗"？多近才算"两个碗"？
- **遮挡频繁**：猫趴在碗上、摄像头被窗帘遮一下
- **状态变化**：碗里水的反光、摄像头镜头的脏污

### §4.3 流水线

1. **SAM 一次性分割**（固定机位）：SAM 按提示分割任意物体，对固定机位一次扫出所有候选物体（"这些是画面里的所有东西"）
2. **提 embedding + 存库**：每个候选物体提一串向量，存入向量库
3. **帧差变更触发重分割**：画面里东西多了/少了/动了/被遮挡——触发 SAM 重分割，更新候选集
4. **新帧物体提特征检索**：新一帧里出现一个物体 → 提特征 → 向量库检索最像的 → 判定是否同一个

OWLv2 图像引导作对照（"拿这个碗的照片当查询"），GDINO 文本提示作备档（"bottle"/"cup"——但 [之前裁定全误框](3 号《模型》§4)，暂撤下）。

### §4.4 对比学习视角

| 概念 | 工程实现 |
|---|---|
| 同物体跨视角/光照应相似 | 同一只碗的特征向量在向量库里聚到一起 |
| 不同物体应区分 | 碗 vs 砂盆 vs 摄像头的向量分开 |
| 边界 | 检索阈值的设定（什么相似度算"同一个"）——这是工程难题，本项目仍未解 |

### §4.5 历史裁定背景（重要）

`multi-object-detect-gate` 验收时（2026-09-15）测过碗/摄像头对 GDINO 文本检测的表现：
- **碗**：100% 全误框（碗/碗/食物/饮料 都框不准）
- **摄像头**：召回 4/1859（千分之 2.2）

裁定：碗/摄像头这两类**撤下 GDINO 文本提示路线**，统一走 RAG 式（SAM 候选 + embedding 检索）路线。所以本节是"被 text-GDINO 否定、走 RAG 的替代方案"。

## §5 统一登记-检索抽象（D9）

猫与物体走同一套抽象：

```
登记照 / 嵌入向量库 / 向量索引 / 检索阈值 / 未登记标记位
```

好处：代码一套两业务复用；未来加新对象类型（猫窝、自动喂食器）不需要重写管线。

`registry-retrieval` change 是这套抽象的原始设计记录。
