# 实验方法论

> **为什么需要它**：本项目已有多次「跑了但没留证据」的返工——例如门控标注那次，
> 跑了 1 万帧却没先做 baseline 与可辨识性检查，结果「YOLO 说 62% 无猫」被当成事实往下推，
> 直到 400 帧分层复核才发现是**分辨率问题**（640→1280 有 57% 翻转），白跑一轮。
> 铁律：**做完实验不记录 = 没做**；**没 baseline = 数字是噪音**。

## 核心流程

```
读本 skill → 建/复用 openspec change → 准则写进 design 条款（含面向报告规划）→ 开分支（一个 change 一条）
→ preflight（资源）→ env_check（代码/环境）→ baseline → 可辨识性检查 → 假设 → 对照
→ 验证/推翻 → 修复（一修一 commit）→ 结论写进 change 的 evidence → 生成实验报告 → 合并回主分支 → 删分支
```

### 0.1.1 面向报告规划（设计期就写清）

每个实验从报告出发规划执行：在 design 中写明**读者**（自己回顾 / 团队 / 外部评审）、要回答的验证问题、
对照与验收标准；列出指标的**单位、样本量、来源与局限**；确定案例选样规则（哪些输入值得展示、失败案例怎么选）
与需要采集的产物（对比图、逐轮指标、日志切片）。失败或数据不足时如实记录，不能把预期写成结果。
计划变化时先更新 change 并记录原因。

## 0. 开工前的强制检查

### 0.1 先有 change，再动手

实验挂在 `openspec/changes/<change>/`：范围/验收/非目标进 proposal+design，步骤进 tasks，
**过程与结论进 `evidence.md`**（这是唯一结论载体，不写进对话就算没做）。

### 0.2 隔离：一个 change 一条分支

```bash
git checkout -b exp/<change>          # 从 main 起
# … 实验与修复都提交在这条分支上
# 合并回 main 在主分支工作区做，结论必须已进 change artifacts
git checkout main && git merge --no-ff exp/<change> && git branch -d exp/<change>
```

worktree **只在用户明确要求时**建（不是 agent 的判断项）。共享工作区被他人占用 →
先按 0.3 判断，有人用就停下来问。

### 0.3 资源：GPU/CPU 被占或紧张，不许开跑（强制）

统一入口是 `remote-ops` skill（本仓已移植），**不要自己写检查**：

```bash
SD=.claude/skills/remote-ops/scripts
bash $SD/preflight.sh --gpu-index 0        # 退出码 2 = 容量被占 → 停下问用户，禁止抢占
bash $SD/remote_run.sh --gpu-index 0 --max-cpu-pct 250 --timeout-s 3600 -- <cmd>   # 长任务一律包起来
python3 $SD/code_audit.py audit <script>   # 先静态审内存炸弹（循环累积帧/无 no_grad/无上限 while）
python3 $SD/code_audit.py smoke --cap-mb 2000 -- <cmd with {n}>   # 降规模测峰值 RSS 再外推
```

**判 GPU 忙不忙看有没有进程真占显存（≥500 MiB 即忙），不看瞬时利用率。**

### 0.4 环境是实验的一部分（跑之前核验）

```bash
bash $SD/env_check.sh --env plf --expect-commit <sha> --json results/<topic>/<run-id>/env.json
```

要落进 `env.json` 的六项：代码 commit/分支、解释器与关键库版本（torch/cuda/cv2/transformers）、
权重路径与大小、GPU 型号/驱动/时钟/功耗、可用显存与 load、seed 与输入 hash。
**远端 HEAD 与自己分支不一致 → 那一轮数据作废**，不要「先跑跑看」。

## 1. 先分清实验类型（证据不一样）

| 类型 | 典型问题 | 主要证据 | 不接受的替代 |
|---|---|---|---|
| 性能/效率 | 延迟、FPS、显存、吞吐 | 量化指标 + 干净测量环境 | 「看起来更流畅」 |
| 感知/质量 | 动作识别准不准、掩码质量、图好不好看 | **人眼盲评**（固定随机顺序、原始分辨率、并排对比）；自动指标只作诊断 | 拿自己优化的那个标量当验收 |
| 正确性/一致性 | 接口可导、闭环误差、坐标换算 | 恒等式、注入已知量恢复、单元测试 | 单个成功案例 |

### 1.1 baseline 先跑，数值落盘

关掉所有开关先确认问题真实存在；baseline 数值写进 `evidence.md`，作为后续每轮锚点。

### 1.2 可辨识性检查（优化之前做）

判据得能分辨目标变化，三种做法任选：**注入已知量再恢复**（能否测回、精度多少）/
**判据落差 vs 噪声底** / **重复测量得抖动幅度**（小于抖动的改进不算改进）。

本仓实例：400 帧同子集比较「整图 vs 2×2 vs 3×3 分块」的 cat 检出数（174/228/略增），
这是**判据落差**；先做它，才没有把「分块=分辨率」误判成「模型不行」。

### 1.3 两个「是」必须分开证

- **问题存在**：baseline 显示差异真实存在；
- **方法有效**：干预后同一个量确实改善。

同一个量不能同时承担两件事。反例：门控阈值按「漏检≤2%」反解时取了**最低**阈值 → FPR 100%，
「召回 100%」其实等价于「全判有猫」，指标变好但方法无效（已修，见 `presence-gate-model`）。

### 1.4 量化与人眼的分工

性能类量化优先；**感知/质量类人眼是验收、自动指标是诊断**。盲评规格：原始分辨率、同位置并排、
随机顺序、文件名不含修正标记、逐对记「对/勉强/不对 + 一句原因」。

### 1.5 样本量门槛

`n=1` 只算**管道验证**（证明链路能跑、产物格式对），不得据此下质量结论。设计阶段就写清需要
多少帧/多少段/几个 seed 以及为什么够。达不到就写「未验证」，不要用「初步看起来」代替。

## 2. 对照设计

- **假设可证伪**：写「预期 X 让 Y 从 A 到 B，因为 W」，跑完不成立就推翻，不要硬调参。
- **一次只改一个变量**（用于归因的轮次）。
- **对照同输入**：同帧、同 seed、同 hash；跨 run 比较前先证明环境等价（§0.4）。
- **反事实**：不仅「某量变小」，还要说明**该量变小等价于目标变好**。
- **自证循环防护**：诊断量不得与优化目标同源；每个指标要能回答「它不测量什么」。
- **失败边界优先**：失败案例/失效条件单列，比成功率信息量大。

## 3. 执行与污染控制

- 每轮开跑前跑一次 `preflight`；与他人并发的轮次**显式标注为污染数据**，中途发现污染的，
  污染窗口内所有 run（含复测 baseline）一律作废重跑。
- 长任务包 `remote_run.sh`，日志 + 进度打印（每 25–200 条一次），否则无法判断是在跑还是卡住。
- **每跑完一次立刻追加一条记录**（不等全部做完）：做了什么 + 数据 + 结论/下一步，一条 ≤120 字。

### 3.1 产物落盘（强制）

| 内容 | 路径 |
|---|---|
| 一次运行的全部产物 | `results/<topic>/<run-id>/`（`results/` 已 gitignore） |
| 大资产（权重/参考素材） | `results/<topic>-assets/`（只读复用，不进 run 目录） |
| 可复用脚本 | `scripts/` 或 `.claude/skills/<skill>/scripts/`（**必须提交**） |
| 一次性探针 | `tmp/`（可不提交，但结论必须转写进 evidence） |

`<run-id>` = `<小写短描述>-<YYYYMMDD><轮次字母>`，例 `native-gdino-20261028a`；禁止 `test2`/`final`/`new`。

每个 run 目录必须自带：`metrics.md`（人能看懂）、`summary.json`（机器）、`env.json`、
`execution_status`（完成/部分完成/失败）。**失败的 run 也留目录，不删。**
数字与结论必须回写 `openspec/changes/<change>/evidence.md`——只留在远端等于没做。

## 4. 修复纪律

- **动手前先有回退路径**：代码走独立 commit（回退 = `git revert`），配置记原值，远程状态记还原步骤。
- **一次修复 = 一个 commit = 一条证据记录**，commit hash 与回退命令写进 evidence：
  ```markdown
  - commit `<hash>`：<改了什么 + 为什么 + 影响面>。回退：`git revert <hash>`。
  ```
- **最小侵入**：能用参数开关就不改默认行为。
- **修复后跑完整对比验证**（不只跑出问题的样本）；回归失败就回滚。
- **无收益的改动与失败的改动同等对待**：数据表明无效就 revert，并把根因写进 evidence。

## 5. 文档化

### 5.1 `evidence.md` 段落骨架

```markdown
### <YYYY-MM-DD>：<实验标题>（<run-id>）

- **skill 闸门**：是否加载本 skill（是 / 否 + 原因）
- **类型**：性能 / 感知质量 / 正确性
- **baseline**：<数值与出处>
- **可辨识性**：<注入恢复 / 判据落差 / 重复测量>
- **对照**：<同输入说明 + 各臂设置>
- **结果表**：<数字>
- **这个指标不测量什么**：<一句话>
- **样本量**：<帧/段/seed；是否达门槛>
- **失败边界**：<失败案例与失效条件>
- **结论与其上界**：<能说到什么程度>
```

被推翻的结论**留痕不删**，单列「对旧结论的更正」表：`| 旧结论 | 出处 | 更正 |`。

### 5.2 结论的上升路径

反复验证、稳定成立的结论上升进 `openspec/specs/`（走 `openspec-sync-specs`），成为后续 change 的默认前提。
**不再维护第二份领域 notes**——两份必然不同步，错的那份会被下一次实验当前提读进去。

### 5.3 图片/视频

对比帧、曲线、失败边界特写放 run 目录；需长期保存的少量关键图进报告的 assets 目录（见 §5.4），
或 wiki 文档场景走 `management/docs/_assets/<slug>/`（文档流程）。体积纪律：图 <1MB，视频转 H.264 <10MB。

### 5.4 实验报告（实验结束后生成，强制）

实验结束后**必须**生成可审阅的报告，执行失败或部分完成也保留草稿并说明缺失——报告记录的是
「这次实验证明了什么/没证明什么」，失败的实验同样有此义务。报告进 `management/experiments/`，由脚本生成：

```bash
python3 .agents/skills/experiment/scripts/build_report.py --help   # 作者清单驱动的生成器
```

约定（详见 `management/experiments/README.md`；写作骨架与叙述字段见 `references/report-template.md`）：

- 落点 `management/experiments/<topic>/<YYYYMMDD>-<主题短名>/`：`report.md`（frontmatter：title/date/run_id/status/verdict/summary/source + 正文）、`metrics.json`（series + tables）、`manifest.json`（evidence 六项 + metrics + cases）、`assets/`（案例图，作者显式选择，不自动扫）；
- **一主题一篇**：同一主题再做一轮就更新同一篇，不新增第二篇；版本信息只进附录「运行谱系」表（日期 / run id / 做了什么 / 执行状态 / 产物），正文按子问题组织。合并多篇时正文数字必须能在引用的产物或来源文档里找到原值，跨轮不可比的单列说明。标题写「对象 + 对照或范围」、≤24 汉字，不塞成绩与结论；
- `status`（执行状态：complete/partial/failed）与 `verdict`（结论方向：improved/no-gain/worse/inconclusive）独立填写；
- **正文是面向读者的文章，不是指标清单**：依次使用「背景与目标」「当前问题」「实验设计」「结果与分析」「结论与下一步」，最后提供「附录：配置与完整数据」。先介绍背景和术语，再提出问题；正文只保留能帮助判断的数值、图表和媒体并就近说明含义与限制。完整指标、精确配置、版本、权重、哈希、命令与原始来源放入附录（网页默认折叠）。不得把原始 metrics.md 直接拼进正文，也不得自动铺满指标卡片。核查数据齐全不等于文章清楚，两项均须审阅；
- **incomplete 由脚本与后端按同一规则推导**（frontmatter 必填 + 文章章节齐全 + evidence/案例齐全 + sha256 匹配），不由作者自评；缺什么就在 diagnostics 里写什么；
- 案例 `src` 指向 run 产物或仓库内图片，生成器复制进 `assets/` 并计算 sha256；报告 `source` 指向 run 产物路径（如 `evaluation/results/*.json`），不复制大产物；
- 报告页在前端 `/management/experiments` 审阅（正文文章 + 折叠附录 + 结构化指标/趋势）；媒体一律嵌在正文对应位置，页面不设单独的案例区；
- 生成或合并后用 `python3 scripts/checks/check_experiment_reports.py` 校验：逐篇按后端同一规则判完整度，并核对正文里嵌入的 `assets/`、`media/` 是否都已在 cases 登记（未登记不会被 media 路由放行）。

与 evidence 的关系：evidence 是过程记录（即时追加），报告是面向读者的结论交付（事后整理）——两者都要，不互相替代。

## 6. 反模式

| 反模式 | 应该怎么做 |
|---|---|
| 没跑 baseline 就说「改好了」 | 先跑 baseline 确认问题存在 |
| 一个量既当优化目标又当验收 | 引入不参与优化的诊断量，或人眼盲评 |
| n=1 就下质量结论 | 只当管道验证，写清样本量门槛 |
| 只报「某量变小」不说它等于目标变好 | 补反事实与等价性论证 |
| 归因轮次同时改多个变量 | 只改一个；搭工具可以多件一起落 |
| GPU 忙着照跑，事后标注污染 | 先停下问用户；抢占可能毁掉别人的会话 |
| 裸跑长任务（不限线程、不设超时、无看门狗） | `remote_run.sh` 包起来，四道闸 |
| 只查 GPU 不查 CPU/内存/磁盘 | `preflight.sh` 一起看 |
| `pkill -f python` 收尾 | 只杀自己这次的 pid |
| 在单次 ssh 里 `nohup … & disown` | 用 `setsid nohup` 或 `remote_run.sh` |
| 结论只写在对话或代码注释里 | 写进 change 的 evidence，结束后生成实验报告（§5.4） |
| 做完实验只写「完成」 | 必须有数据 + 对比 + 结论 + 上界；报告 status/verdict 如实填 |
| 报告只报成功案例 | 案例由作者按选样规则显式选择，失败边界单列（§2） |
| 把原始 metrics.md 拼进正文 / 自动铺满指标卡片 | 正文按报告问题组织关键数值并就近解释，完整数据进折叠附录（§5.4） |
| 每跑一轮就新增一篇报告，主题下一堆版本目录 | 一主题一篇，版本进附录「运行谱系」，正文按子问题组织（§5.4） |
| 正文嵌入的图/视频没登记进 cases | 登记后再嵌入，或删掉引用；`scripts/checks/check_experiment_reports.py` 会拦 |
| 从运行编号或目录名猜造报告内容 | 缺背景/设计/解释时保留草稿提示，不从目录名推断 |
| 过程记录等最后补 | 跑完一次立刻追加 |
| 无效但无害的改动留在仓库 | 无收益即 revert，evidence 记根因 |
| 推翻旧结论后静默删掉 | 留「对旧结论的更正」表 |
| 远端停在 main 却跑自己分支的实验 | `env_check.sh --expect-commit`，不一致即作废 |

## 7. 与其他 skill 的分工

| 事项 | 去哪 |
|---|---|
| 怎么连/预检/守卫/代码审计/环境核验 | `remote-ops` |
| 训练、测试、speedrun、评测的具体命令 | `training` / `testing` / `speedrun` / `evaluation` |
| 数据集与权重位置 | `datasets` |
| 文档写作与 Wiki 约定 | `documentation` |

**与 `evaluation` 的边界**：本 skill 管模块无关的方法论（假设、baseline、对照、证据标准、样本量、失败边界）与实验报告；
`evaluation` 管评测模块的操作（模型/数据集/配置 CRUD、跑评测、结果对比）。评测 run 作为实验证据时，报告
`source` 指向 `evaluation/results|outputs/` 产物，本 skill 引用而不复制其操作指南。
