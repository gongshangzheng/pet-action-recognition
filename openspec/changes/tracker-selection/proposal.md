# Proposal: tracker-selection

> 子 change，总管：`pet-motion-latent-pipeline` §4A。**状态：重启（2026-09-17）**——原为「延后等出现多猫」，现改为**主动核实 + 选型**。

## Why

**原延后理由已失效**。原写「单猫白天场景抽样+插值已验收足够，多猫数据出现时启动」，但：

1. **「单猫」是未核实的假设**，不是测量结果——该说法只出现在管线脚本注释里（`# 猫主轨迹关联（最高置信框，单猫场景）`）；且批处理报告**自己就打了问号**：「两个严重偏低段（100505/180330）待人工排查：**多猫？**猫不在画面？场景问题？」——**该问号从未回答**
2. 语料是 **2 个家庭**（`cui` / `jiang`），**每户几只猫未知**
3. **若确有多猫，当前管线已静默出错**：`entry["cat"] = 最高置信框`（一行 argmax）遇到两只猫会在两者间**跳变**，插值 + 平滑再把跳变铺成一条**平滑但荒谬的路径**——不报错、只产出垃圾，且下游（行为发现）会把它当数据
4. **单猫场景也有收益**（原 proposal 漏了）：
   - **离场/遮挡的 `lost` 语义**——当前插值无「缺席」概念，猫离场时 `np.interp` 会画一条**穿墙直线**（这是已知短板）
   - **误报抑制**——ByteTrack 的「低分检测二次关联」天然过滤误报（沙发事故的同类问题）
   - **多猫同框时锁定目标**——只跟关心的那只、排除另一只

**另外**：原「否决」与「延后」被混为一谈——被否决的是**全帧率检测 + ByteTrack**（成本高 + v5 实测观感更抖）；而**关联器只跑在抽样帧上**（检测次数不变、成本近乎为零）这个组合**从未被评估**。

## What Changes

- **前置闸门（新增，必须先行）**：多猫核实——抽段看原始视频，数清每户几只猫。这是**数据质量核实**，成本极低，且结论会反向影响下游（若有多猫 → 已产出的 followcam 需重跑）
- 小样本 GT 制作（3–5 段，人工核对 track_id）
- 固定同一 GroundingDINO 检测源，多候选同台对比
- **对比两组形态**（原 design 只考虑后者）：
  - **A. 关联器只跑抽样帧**（新，低成本：检测次数不变）→ 配我们的插值填中间帧
  - **B. 关联器跑全帧率**（原否决方向，作为对照确认 D1 结论）
- 指标：IDF1（主）/ IDSW / 轨迹碎片数 / 框平滑度 → 选型报告
- **同时评估**：关联器是否**只用于贴 id、不改框位置**（保观感）vs 是否用其卡尔曼预测参与平滑

## Capabilities

### Modified Capabilities

- `motion-pipeline`: 跟踪环节由「抽样 + 插值（无显式关联）」升级为「抽样关联 + 插值」，获得 track_id 语义（多目标关联、离场/遮挡的 lost 状态）

## Impact

- 选型实验为主，`petlib/tracking/` 五实现已就位（契约测试 13 过）
- **可能的重跑**：若核实有多猫 → 受影响的 followcam 段需重跑（现状只跟了一只猫）
- 结论决定 `spot-check-cli` 的默认跟踪器
- **不再以「多猫数据出现」为触发**——触发改为「核实结果 + 用户批准实施」
