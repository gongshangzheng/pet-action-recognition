# Design: resource-guard

## 事故与既有方案

门控标注期间曾观察到 load average 达 103、连接中断。详见历史证据和 Git 历史。D6 已由用户确认：采用现有 `remote-ops` 的预检、限额看门狗及采样日志，超限时终止，不暂停或恢复。

## 预检与运行

调用入口应在共享机运行前执行预检，资源不足时拒绝启动。运行时对受控进程树采样，超限时终止并留日志；不控制其他用户进程。采样具有时间间隔，不承诺瞬时绝不超限或保证他人完全不受影响。不得用 force 或允许忙卡等选项绕过共享机纪律。

现有实现使用 shell 护栏及调用封装；先按 tasks 核对具体入口、阈值、日志和停止行为，再决定是否需要修正。不要把原先假定的 Python 模块、SIGSTOP、恢复机制或 12 GB 占用演练当成合同。

## 证据边界

短 CPU 真实进程可验证预检拒绝、超限退出及进程树停止和日志，不能证明 GPU 或共享机行为。真实 GPU 和共享机验证须事先取得执行授权并通过资源预检，不擅自安装环境。已有测试一次在调用 guard 前发生文件读取竞态，另一项仅运行 sed/awk 而非生产 guard，均不足以证明生产缺陷，详见 `evidence.md`。

原 `resource_guard.sh` 有用户未提交修改；若实施需要接触该文件，必须停止并由父审阅、单独授权是否纳入原 patch。不得强行覆盖或把来源树当权威覆盖现有文件。

## Open Questions

真实 GPU 和共享机安全验证的时间与资源授权尚未确定；具体阈值须按实际环境及用户确认核定。
