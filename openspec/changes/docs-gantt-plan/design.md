# Design: docs-gantt-plan —— 本篇的结构（唯一依据）

## 1. 读者动线

读者是负责人和三名执行人，来的场景只有三种：**看整体什么时候到哪一步**、**看自己这条线该干什么**、**卡住了怎么降级**。所以顺序定为：时间线（一句话能看完）→ 图（一眼看全）→ 分工（按人找活）→ 检查节点（按天验收）→ 与其他文档的关系 → 重渲染方式。

不写的内容：模型设计细节归《动作识别模型设计》、端侧实现归各 change、里程碑长期规划归 `milestones.md`。本篇一旦开始解释「为什么用 VideoMAE」，它会和另外两篇同时腐烂。

## 2. 目标结构

| 章 | 内容 | 读者问题 |
| --- | --- | --- |
| 一、时间线 | 四个节点的日期与一句话含义 | 什么时候交什么 |
| 二、甘特图 | 一张图 + 图例 + 图片尺寸例外说明 | 谁在什么时候忙什么 |
| 三、三条并行线 | 算法训练 / 硬件组 / 端云集成，每条线一张表：时间、工作、产出或依赖 | 我这条线干什么 |
| 四、检查节点 | 时间、核验什么、不通过怎么办 | 哪天被卡、卡了怎么办 |
| 五、与其他文档的关系 | 指向 `milestones.md`、`architecture`、`action-model-design` | 还想看细节去哪 |
| 六、重新渲染 | 渲染命令与 skill 指向 | 排期改了怎么更新图 |

## 3. 写作约束

- **每条任务都带依赖或产出**，不写「推进 XX」这类无法验收的动词
- **人数与分工写实**：硬件组给的是序列号读法与 SDK，不是「协助集成」；协助要写成具体交付物与最晚到货时间
- **不写进度的历史**：改过一次排期不写「原先如此，现改为」，只写现在是什么
- **降级预案必须写具体动作**（如「跟拍先降级为手动」），不写「视情况处理」
- **图的尺寸例外要写明理由**：本篇甘特图 1884px 宽，超过图片规范 1600px，原因是条内中文标签可读性，不允许后续无理由放大

## 4. 与里程碑表的分工

| | `milestones.md` | 本篇 |
| --- | --- | --- |
| 粒度 | M1–M6 长期节点 | 冲刺期逐日 |
| 生命周期 | 全项目 | 11.11 – 11.23 |
| 冲突处理 | 以本篇为准 | 回写里程碑表对应日期 |

## 5. 图的产出方式

遵循 `report-figures` skill：`.mmd` 源 + `mermaid-render-config.json` 主题 + 2 倍 PNG 与 SVG 同时出。甘特图的 `leftPadding` 必须留出泳道名宽度，`todayMarker` 必须关闭（静态图里的「今天」红线会被误读成任务标记）。
