# Proposal: presence-gate-model

## Why

架构 §4 把「在场门控」定为环节①的**第 0 步**：监控视频大部分时间可能没有猫，没有猫就不该往下跑检测跟踪 / 跟随裁剪 / 抠像 / 表征 / 分割 / 识别。§4 同时明确 **GroundingDINO 退出 门控**（太慢），改用可高频运行的轻量模型；§2 也把「门控轻量模型选型」列为 🟡 待定项。

但现状是：**没有任何 change 承接这件事**。

- 34 段批处理报告里的「在场率 0.939」是**用 GroundingDINO 每 10 帧抽样检测算出来的**，不是门控模型；
- 门控漏了后面全漏（架构原话），所以它是全管线风险最高、成本最低的一环；
- §4 已裁定的**空白时段三分法**（在场静止 = 动作类别「静止」/ 出画死角 = 标注「不在场」不得计静止 / 被遮挡 = 标注「无法测量」）同样**没有任何实现载体**——三分法的判定来源就是门控。

## What Changes

- 新增**在场门控**：判定「当前帧画面里有没有猫」，输出在场时间轴与在场率，驱动管线早退。
  **门控是逐帧图像模型**（输入单帧图像或多尺度单帧特征，输出该帧「有猫」概率）；
  时间维度只在两层里：**调度**（每 K 帧跑一次）与**后处理**（区间合并 / 迟滞 / 最短持续时长）——不进入模型结构，不存在「视频门控模型」。
- **候选方案四组同台实测**（含用户 2026-10-27 提出的「复用 GroundingDINO 内部特征 + 薄 MLP」方案的两个变体）：
  - A. 现成轻量检测器：YOLO11n 单类「猫」（256–320px 输入）
  - B. 轻量二分类器：MobileNetV3-Small / ShuffleNetV2 在 224–256px 上做「有猫/无猫」
  - C1. **GDINO Image Features（Feature Enhancer 之后）+ 薄头**（用户提案）
  - C2. **GDINO Backbone 输出（Feature Enhancer 之前）+ 薄头**（纯视觉特征，可跳过文本编码器与增强器）
  - 基线 D：帧差 / MOG2 运动能量（零训练参照，用于说明"只靠运动不能判在场"）
- 评测协议（**召回优先**）：以漏检率为主指标，其次误检率、单帧延迟、门控频率敏感性、夜视段表现；弱标签来自既有 GDINO 轨迹（蒸馏标签），另设**人工核验集**避免只跟老师学盲区。
- 集成：门控早退跳过环节②–⑧ + 在场时间轴 + 三分法判定字段；与 `batch-followcam-extraction` 已产出的 34 段报告口径对齐。
- 硬件目标：服务器侧（pet 4090）与边缘侧（RV1126B，供 `verify-company-module-workflows` 引用）分别给延迟估算。

## Capabilities

### New Capabilities

- `presence-gate`: 在场判定的输出契约（在场时间轴 / 在场率 / 三分法状态）、召回优先的阈值策略、早退语义与不可用情形声明。

## Impact

- 新增 `petlib/gate/`（判定器抽象 + 三个实现）+ 评测脚本；训练/评测产物落 `results/gate/`。
- 与既有状态层解耦：门控只判「有没有猫」，不做识别、不改猫框（框仍由 `multi-object-detect-gate` 的检测跟踪层负责）。
- 夜间红外段（45 段）不在 v1 管线范围内，但**门控必须在夜视段上单独验证召回**，否则会把「无法处理」误标成「不在场」。
- 消费方：`spot-check-cli`（报告三分法）、`realtime-exit-sse`（实时早退）、`video-*`/`identity-*`（省算力）。

## 不做

- 不做多类检测（只判「有猫 / 无猫」）；不做猫框回归。
- 不负责「哪只猫」（属 §10 身份）与「猫在哪」（属 §4 主检测跟踪）。
- 不引入新的标注工作量：弱标签 + 少量人工核验帧。
